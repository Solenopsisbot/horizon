# Java mod compatibility checklist

Status: active work for Minecraft 26.3. The implementation is tracked in [issue #6679](https://github.com/horizon-rust/horizon/issues/6679). This page is the short progress view; [java-mod-compat.md](java-mod-compat.md) remains the design and phase plan.

Last checked: 5 November 2026, after the Knot-launch, call-compat and config-gate wave (code through commit `15d7d537b`; verified against NeoForge 26.3.0.101).

## Supported now

- [x] Read Fabric `fabric.mod.json`, NeoForge `neoforge.mods.toml`, and legacy Forge `mods.toml` for bounded identity, dependencies, client-only markers, and entrypoint discovery.
- [x] Discover and run multiple Fabric entrypoints in deterministic order, including object/array containers and the `main`, `client`, `server`, and `preLaunch` kinds. The JVM fallback rejects unknown entrypoint adapters before starting a JVM.
- [x] Discover NeoForge and legacy Forge `@Mod` classes through the native probe path, including multiple classes in one jar.
- [x] Run the real NeoForge/FML loader through `horizon-jvm`: `--real-loader --entry-kind neoforge` resolves the installed server's `unix_args` classpath/versions, runs FancyModLoader in a child JVM (discovery, Minecraft bootstrap, `IEventBus` mod construction, common init) and reports completion. The fixture verifies both the direct probe and this runner path against installed NeoForge 26.3.0.101 and 26.1.2 servers. `--list-fml-mods` reports sorted `id<TAB>version` rows without running entrypoints, and `--fml-report` (`--json` optional) reports status, server, jars, mods, initialization and the first error, all bounded.
- [x] Preflight the real NeoForge loader on server startup: when `HORIZON_NEOFORGE_SERVER` (an installed server) and `HORIZON_JVM_BIN` (the `horizon-jvm` binary) are set, the integrated and dedicated server run the FML child probe once before the native path, log a bounded report naming the role, jar count and mod ids, and never run it for a client. A failure is log-only unless `HORIZON_NEOFORGE_STRICT=1`, which stops startup with the failure reason.
- [x] Probe the real NeoForge/FML loader: `tools/neoforge_loader_probe.py` drives FancyModLoader 11 against an installed NeoForge server, discovers a real `@Mod` jar, bootstraps Minecraft, constructs the mod with its `IEventBus`, and runs common initialization. This proves the FML lifecycle outside Horizon; `horizon-jvm --real-loader --entry-kind neoforge` now provides the same lifecycle on 26.3.
- [x] Run the real Fabric loader lifecycle: `--real-loader` installs a bounded launcher, calls `FabricLoaderImpl.load()`/`freeze()`, and invokes the loader's own entrypoint containers (`main`/`client`/`server`). `tools/fabric_loader_probe.py` builds a real `ModInitializer` jar and proves the loader discovers and runs it (4 mods, 1 entrypoint). `--game-jar`/`--game-version` now select the loader's real `MinecraftGameProvider` over the supplied game jars (with `--provider-report`), with `isDevelopment` following the production path by default, bounded freeze failures reported, opt-in `--real-launch` stub hand-off, `--fabric-discovery` loader-owned discovery, and opt-in `--classpath-unlock` registering the game and mod jars on a real Knot class loader (verified by a byte read-back; 46 jars on 0.20.1), with Knot transformer initialization behind the same flag (`knot-init: ok <n> transformers`) and `--knot-launch` handing the Knot loader to the launcher and proving a loaded class's bytes travel the transformer chain (`knot-launch: ok <n> transformers, transformed=<class>`). A gated integration test runs a real Fabric server mod against a Minecraft 26.3 server jar, sees `minecraft 26.3` plus the fixture in the loader list, enters the production provider and runs its server entrypoint; real intermediary-to-official remapping and true game launch remain missing.
- [x] Run unsupported entrypoints through the embedded JVM runner as a fallback; `--list-entrypoints` reports discovery without starting a JVM, and NeoForge toml/jarJar/mixin markers are surfaced as diagnostics.
- [x] Keep the execution decision explicit: bounded entrypoints and typed declarations use the native Rust host
  path first; unsupported calls and required transforms carry a named reason into the `horizon-jvm` fallback.
  Native execution is not a translated Rust jar, and a JVM fallback is not counted as native coverage. The tier
  model and evidence rules are documented in [java-mod-compat.md](java-mod-compat.md#native-first-strategy-and-tiers)
  and [java-mod-distribution.md](java-mod-distribution.md#2-compatibility-tiers).
- [x] Expose bounded Fabric loader values: loaded-mod checks, metadata (including authors/contributors/license collections and icon-path optionals), versions, environment type, development marker, root paths, seeded containers, and identity `MappingResolver` queries.
- [x] Expose bounded NeoForge and legacy Forge loader values: mod lists, containers, event-bus access, mod ids, and role-aware client/server selection.
- [x] Register and inspect bounded NeoForge and Forge deferred registrations, holders, registry objects, keys, ids, entry collections, generated `Registry.getHolder`/`getOrThrow` lookups, explicit typed-registration handoff, typed recipe and ingredient data-file declarations, `Item.Properties` stack/durability/crafting-remainder/fire-resistance values, bounded `BlockBehaviour.Properties` strength/resistance/friction/occlusion/tool/random-tick values, `EntityType.Builder` category/dimensions and mob lifecycle values, and `ItemStack.getUseAnimation`/tag-stream façade coverage, and custom payload type identity.
- [x] Infer typed `Item`/`Block` declarations from ordinary Java construction: `Item.Properties` (`stacksTo`, `durability`, `rarity`, crafting remainder, fire resistance) and `BlockBehaviour.Properties` (`strength`, `friction`, speed/jump factors, random ticks, occlusion, tool requirements) chains are recorded on the constructed value marker, and a plain `Registry.register` exports `max_stack_size`, `rarity`, `crafting_remainder`, `hardness`, `explosion_resistance`, `friction`, and `requires_tool`. Explicit `META-INF/horizon-native.json` declarations still override inference. Inferred items/blocks name the real vanilla `minecraft:stick`/`minecraft:stone` templates so the content planner can resolve them.
- [x] Record Fabric events, NeoForge events, and legacy Forge event-bus listeners with ordering, cancellation markers, unregister support, and Forge `register(Object)` handlers.
- [x] Record custom payload registrations for the supported Fabric/NeoForge directions, retain custom payload type identity, and support the bounded legacy Forge `SimpleChannel.registerMessage` alias, with bounded `FriendlyByteBuf` value round trips.
- [x] Implement a real bounded `FriendlyByteBuf`: a 1 MiB big-endian buffer with a read cursor round-trips primitives, varints, UTF-8 strings (`writeString`/`readString` included), identifiers, UUIDs, block/chunk positions, byte arrays, boolean/long/float/double/string arrays and VarInt int arrays (`writeVarIntArray`/`readVarIntArray`, with `writeIntArray` aliased), nullable/optional values, and enum ordinals, plus cursor operations (`readerIndex(int)`, `writerIndex(int)`, and `setIndex`). NBT remains an opaque bounded marker.
- [x] Extend the bounded `FriendlyByteBuf` façade with signed little-endian short/int/long/float/double and signed 24-bit medium read/write pairs, with source-built compile and round-trip coverage.
- [x] Provide bounded NeoForge and legacy Forge capability/`LazyOptional` markers, NBT values, identifiers, resource keys (including `ResourceKey.location`), capability `orEmpty`/`orElse` values, bounded declared-field reflection, arrays, reflection metadata, collections (including `removeIf` and `Iterator.forEachRemaining`), maps (including `entrySet`/`Map.Entry` equality and hashing, `computeIfPresent`, and `merge`), primitive optionals (`OptionalInt`, `OptionalLong`, `OptionalDouble`), streams (including runtime-owned `toArray` results and `Collectors.toList/toSet`), and optionals.
- [x] Provide common Java wrapper/string/collection operations used by loader bootstrap code, including integer/long/float/double/byte/short/character conversion, `Number` accessors, checked math, seeded `System.currentTimeMillis`/`identityHashCode`, seeded `System.getProperty(key, default)` and `System.getenv` queries, deterministic `Thread.currentThread`/`getName`/`isDaemon`/`getContextClassLoader` markers, bounded callback combinators, `Arrays.asList`, `Objects.hashCode`/`requireNonNullElse`, and a restricted `String.format` subset.
- [x] Close the common reflection gaps: primitive `TYPE` classes, reflective argument unboxing, `Field.get/set`, enum constants/`values()`/`valueOf`/name/ordinal through the superclass, bounded annotation proxies, record `equals`/`hashCode`/`toString`, and `Constructor.newInstance`.
- [x] Provide bounded `ClassLoader.getResource`/`getResourceAsStream`/`getResources` markers from explicitly seeded `StdHost::with_resource` entries and every non-class file bundled in a `NativeJar::seed_host` jar with bounded byte-backed `InputStream` reads, `available`, `skip`, `skipNBytes`, mark/reset, and close support, explicitly seeded `ClassLoader.loadClass` markers, current-jar `Class.forName`, bounded field reflection, and explicitly seeded `ServiceLoader` providers and iterators; these queries never scan host files or the process classpath.
- [x] Discover Mixin translation plans from real annotations: `@Mixin` targets (read from `RuntimeInvisibleAnnotations` too, since real `@Mixin` is CLASS-retention; malformed tables become bounded per-jar warnings, 64 at most) and `@Inject` methods with `method` (name or `name(descriptor)`), `@At` anchors `HEAD`/`RETURN`/`TAIL`, and `cancellable` become deterministic `MixinInjectionPlan`s. `NativeJar::execute_discovered_mixins` runs HEAD callbacks in Mixin's apply order (annotation priority, config `mixinPriority`, config position, method index), the same order the load-time weave uses, the target once, then RETURN/TAIL callbacks on the same target, validating every callback before running any. Execution is config-gated through `execute_discovered_mixins_on`: plans whose class no readable config lists on the selected side, or whose first matching config has a plugin, are skipped with a bounded reason, and legacy Forge `META-INF/MANIFEST.MF` `MixinConfigs` declarations are read. Cancellable HEAD plans get a runtime-owned `CallbackInfo`; `cancel()` stops the remaining callbacks and the target and returns the default value. RETURN/TAIL callbacks get a `CallbackInfoReturnable` carrying the real result, and `setReturnValue` overrides it. `@At(value = "INVOKE", target = ...)` plans parse descriptor, slashed/binary `owner.method(...)` and `owner#name` selectors; the interpreter runs their hooks before the matched call (cancellable hooks suppress the call and return the descriptor default) and reports matched sites. A separate `MixinAnchorPlan` path discovers and executes `@Inject`/`@Redirect` at `FIELD` (get/put, cancellation suppresses the access), `NEW` (construction, cancellation leaves null and skips the constructor) and `JUMP` (opcode/offset, cancellation falls through), plus bounded `@Redirect` at HEAD/INVOKE/FIELD; unsupported anchor shapes are reported with a precise reason. `@Overwrite` replaces a target body (one per target, no coexistence with other executable plans), `@ModifyArg` replaces one argument at a matched INVOKE, and `@ModifyVariable` replaces a STORE/LOAD local selected by slot or ordinal; inherited/competing overwrites and unsupported selections stay report-only with reasons. `--mixin-plans` reports plans, unresolved selectors and targets without an entrypoint.
- [x] Preserve every Mixin config/annotation detail in the census: `@At` selector values (`target`, `args`, `ordinal`, `shift`, `by`, `desc`, `id`, `remap`), nested `@Slice` boundaries, `@Group` constraints, Mixin Extras injector families (`wrap-operation`, `wrap-with-condition`, `modify-expression`, `modify-receiver`), config edge values, priority/order metadata, and access-widener/access-transformer discovery including namespaces.
- [x] Expose bounded `EntityType`/`MobCategory`/`SpawnPlacements`/`EntityDimensions` façade values, including builder spawn flags, dimensions, descriptions, despawn distances, and bounded spawn-placement registration state.
- [x] Provide bounded Fabric API bootstrap façades for `ServerLifecycleEvents`, `ClientLifecycleEvents`, `ServerPlayerEvents`, `CommandRegistrationCallback`, `Event`, `FabricLoader`/`ModContainer`/`ModMetadata`/`ObjectShare`, emitted only when the real API class is absent, with ordered handler dispatch. NeoForge `Event` result/cancel and `SubscribeEvent` metadata are also generated.
- [x] Dispatch resident native Java lifecycle callbacks from the server tick: integrated and dedicated servers send `ServerTickEvent.Pre` and `ServerTickEvent.Post` through the ordered listener registrations, while per-role, per-jar hosts retain callback registrations and static state across ticks. A failed callback is isolated to its jar and does not abort the tick.
- [x] Provide bounded client compatibility façades: Fabric `HudRenderCallback`, `ClientTickEvents`, `KeyBindingHelper` and `ItemTooltipCallback` with real ordered dispatch/retention, plus NeoForge `RegisterKeyMappingsEvent` registration state and tick/render event markers. Client signature types are resolved from the game jar instead of hard-coded.
- [x] Provide bounded item-group and renderer registration façades: Fabric `ItemGroupEvents`/`FabricItemGroupEntries` with ordered per-tab `add`/`addAfter`/`addBefore` and search views, `EntityRendererRegistry`/`BlockEntityRendererRegistry`/`ModelLayerRegistry`/`ColorProviderRegistry` retention, and NeoForge tab-contents/entity-renderer events. Every class is emitted only when the real API is absent.
- [x] Provide bounded Fabric networking façades: `ServerPlayNetworking`/`ClientPlayNetworking` retain receivers per payload type, answer `canSend` from the retained map, and record send directions without delivering packets; `PacketSender`, `Context` and the payload handler shapes link. A real Fabric API jar is never shadowed.
- [x] Retain bounded Java host state across native invocations: resident hosts carry jar-owned static fields and initialized-class markers between entrypoint and event callbacks, with caps that reject oversized state; payload registrations and codec markers remain attached to the same host instance.
- [x] Execute the bounded `StreamCodec` façade over `FriendlyByteBuf`: `of`, `unit`, `map`, `dispatch`, `recursive`, and `composite` preserve their encoder/decoder or member state, and primitive/list/optional `ByteBufCodecs` round-trip through the generated codec. Unsupported anonymous codec bodies and shape-only operations remain explicitly bounded.
- [x] Emit a bounded classfile writer and weaver: `ClassFile::write` reproduces input bytes exactly, and the weaver appends a callback `invokestatic` at method head, adjusting `max_stack` and `Code` length. Void methods also get RETURN/TAIL callbacks inserted before every return, and `weave_class`/`weave_classes` apply HEAD then RETURN/TAIL plans per class. Methods with branches, switches, `wide` locals, exception handlers, debug tables and `StackMapTable` frames are relocated correctly (verified by loading rewritten classes), including switch repadding and `goto_w` growth; an `if*` whose target leaves the 16-bit range after an insert is split into an inverted branch over a `goto_w` and the verifier frame for the new fallthrough target is derived with a bounded straight-line type model. `CONSTANT_Dynamic` and `BootstrapMethods` entries are validated and relocated, so a class already using condy (for example javac string concatenation) can still be woven. Non-void RETURN/TAIL callbacks are woven by boxing into a synthetic `CallbackInfoReturnable` and unboxing the override; a cancellable `void` HEAD is woven with a synthetic `CallbackInfo` and a branch around the body. Bounded `invokevirtual`/`invokestatic`/`invokeinterface` call sites can be woven for `@At("INVOKE")` plans, including pop-around-call cancellation for a void callee. Plan-driven weaving applies 0-based/from-the-end ordinals, half-open INVOKE/HEAD/RETURN/TAIL slices and bounded `shift`/`by` insertion (including signed `Shift.BY`) for INVOKE, RETURN/TAIL and HEAD (HEAD `shift`/`slice` is planned but `weave_class_with_extras` currently inserts unshifted), with ordinal-qualified slice boundaries; `@At` selectors are parsed into the plan, and malformed or out-of-range ones stay report-only. Unsupported condy shapes (cycles, illegal handles, malformed rows), `invokespecial`/`invokedynamic` INVOKE sites and general operand-stack rewriting still reject with a reason. `--weave <out.jar>` rewrites a jar end to end.
- [x] Dispatch received payload frames to Java handlers: Fabric receivers are recorded, a frame id resolves through the host packet-type map, and the in-jar handler is invoked with a bounded `payload/<id>/<hex>` argument (plus a context marker); the server tick drains hub frames and routes them. Supported codecs decode before dispatch: UTF-8 string payloads arrive as the string, empty payloads as an empty marker, and raw payloads as `payload-bytes/<hex>`; opaque codecs keep the bounded hex marker. `PayloadValue` gives the transport a typed `Bytes`/`Text`/`Empty`/`Marker` value with bounded decode/encode round trips.
- [x] Expose the payload transport to the Java host: `StdHost` queues Fabric networking sends with channel bytes, publishes them through the declared registry after bootstrap, and accepts received frames; the hub broadcasts queued frames on the next tick.
- [x] Transport Java payload frames over LAN: a declared-channel registry travels on `horizon:payload_channels`, frames use `horizon:payload`, the hub and remote client validate direction and supported codecs (raw/UTF-8/empty) with bounded queues, and send/receive APIs exist on both sides. Mod code can originate frames through networking sends, and received frames dispatch to registered handlers through the bounded payload marker. Client windows drain and dispatch both directions on the client tick with a 256-frame per-tick cap each way: frames the server sent run through a direction-filtered receiver lookup (`dispatch_received_as`), and `PlayToServer` frames the client's Java mods queue leave through a dedicated mirror queue (`take_java_to_server`), so the hub's own drain cannot race them in an integrated game. A handler jar only resolves a frame's channel once it is stored with its bootstrap host (`store_handler_host`), which is what `game/mods.rs` now does; the handler store is keyed by execution role (client / integrated-server / dedicated-server), so an integrated game's client and server roles no longer collide, and the host dispatch passes the concrete role. The hub drain takes only client-bound frames (`take_java_to_clients`), and frames above the 32767-byte custom-payload envelope are split into bounded chunk envelopes (magic `FF H P C`, 64 chunks, joined at the 1 MiB payload cap) in both directions: the client pump and direct send, the client receive assembler, and hub broadcasts; frames within the envelope stay byte-identical to v1. The 64 KiB `horizon:payload_channels` registration is chunked the same way when it exceeds the envelope.
- [x] Content identity covers item-only, entity-only, menu and other built-in registry changes: the overlay marks every non-empty content mod, and the ordered built-in registry report is hashed alongside block states so clients cannot silently reuse a matching block identity after another registry's network ids changed.
- [x] Sync declared Java content to LAN guests: a bounded `horizon:java_content` v3 manifest (epoch plus a 64-bit content hash in the header; v1/v2 frames still decode) (declared ids for blocks, items, effects, entity types, data components, attachments, menus and block entities, block→declared id/template/ticker rows, and bounded menu/entity templates) is sent with the login burst and applied atomically to the guest's global stores, so a guest without the mod jars resolves declared ids and block-entity templates. A declared-content epoch change re-sends the manifest once per guest per epoch, deduplicated by content hash so an applied manifest cannot ping-pong, and a change that lands before a join still reaches older guests. A v3 frame whose hash disagrees with the guest's non-empty local declarations is refused with a bounded once-logged reason and the local content is kept. Malformed, oversized or conflicting manifests are rejected with a bounded reason; block/item templates, menu layout, entity attributes and hot reload are still missing.
- [x] Replace Java declaration tables and capture LAN manifests as one coherent snapshot with an epoch counter, so resource-root refreshes cannot mix ids, templates and menu/entity rows from different generations.
- [x] Persist declared menu clicks in the block entity: a declared menu over a template inventory opens as the matching vanilla chest menu on `Slots::Block`, so server clicks write the block entity and client prediction follows the same path.
- [x] Materialize declared Java block entities on the client: block-state sync and menu opening resolve a declared block to its template entity, so it appears in the client world and its menu attaches to the block; block-entity updates naming the declared id resolve to the template before decoding.
- [x] Persist and tick declared Java block entities: declarations are published keyed by block, saves write the declared id and decode via the template, chunk encoding/worldgen answer the template type, state tickers follow the template or the declared ticker flag, and hopper checks accept declared templates.
- [x] Instantiate declared Java block entities: a declared block entity maps its `valid_blocks` to the vanilla template entity, drives ticker decisions, and reaches placement, `/setblock`, containers and declared menus. Persistence and chunk-flag handling for the declared id still use the template id.
- [x] Show Java mod identity in the launcher: mod rows read Fabric/NeoForge/Forge metadata in place and show loader, id, version, mixin presence and a conservative compatibility hint. The Mods page also shows per-installed-mod probe diagnostics (loader, probe verdict, entrypoints, host calls, registrations, an unapplied-Mixin warning, the stop reason) in a bounded panel of the five most relevant mods with "(+N more)", and a per-mod "Clear compatibility cache" action that deletes just that checksum's cached check so it is probed again.
- [x] Open declared Java menus: a bound block opens a bounded chest menu from its menu declaration, with title, rows and a copied vanilla-template inventory, on the guest/server path.
- [x] Add ABI corpus and differential tooling: `tools/native_java_abi.py` ranks census classes/members/body calls by loader family, and `tools/native_java_differential.py` compares native-probe and JVM-runner outcomes for a compiled fixture.
- [x] Measure a representative fixture instead of guessing: `horizon-jvm --measure [--measure-repeat n] [--measure-timeout secs] [--measure-sample-ms ms] [--json]` times the probe's own argv as a bounded child process and reports startup (to `jvm up:`), total wall time, the child's CPU time and its peak RSS (`VmHWM` where the OS keeps one, `n/a` elsewhere). A sample that exits non-zero, or is killed at the bound, fails the command; killing reaches the child's whole process group. `docs/java-mod-compat.md#measuring-it` records the flags and figures.
- [x] Classify census jars with deterministic native compatibility profiles (`data-only`, `native-safe`, `native-fallback`, `report-only`) and expose the profile rows in `tools/native_java_abi.py` JSON/text output.
- [x] Measure native probe latency in bounded per-method mode: `tools/native_java_perf.py --method CLASS[#NAME]` (repeatable, at most 32) times each named entrypoint on its own through the probe's existing `<jar> <kind> <class>` form, discards `--warmup` runs per method, and reports `warmup`, `p50`/`p95`/`p99` plus `backend` (`cargo-run`/`target-fast`/`target-debug`/`target-release`/`explicit`/`external`) and a `cache` label (`cold` for the first method, `warm` after). The whole-jar `--runs` mode, its `summary` shape and its exit code are unchanged; the probe itself is not modified, so runtime semantics are identical.
- [x] Add an exact numeric value model: `Value::Long` and `Value::Float` cover long/float/double constants, arithmetic, bitwise/shifts, comparisons with NaN polarity, conversions with JVM saturation, returns, locals, arrays, boxing and `Long`/`Math`/`Float`/`Double`/`String` APIs with two-slot arguments and exact constant-pool reads.
- [x] Parse and apply Forge access transformers as well as Fabric access wideners: `META-INF/accesstransformer.cfg` entries (all six access forms, dotted owners, member descriptors, constructors) apply to parsed classes with descriptor-specific matching and missing-target errors.
- [x] Carry nested Fabric JiJ and NeoForge JarJar content into the port output under the nested mod namespace, with bounded files/bytes, deterministic conflicts and skip reasons.
- [x] Parse and apply Fabric access wideners: `accessWidener v1` class/method/field entries with accessible/extendable semantics are validated and applied to parsed classes, preserving constructors and reporting missing targets.
- [x] Parse Fabric and NeoForge dependency metadata: per-mod depends/recommends/suggests/conflicts/breaks maps, sides, orderings, version ranges and nested jar entries, with bounded ids and line-context errors.
- [x] Merge declared content ids into command registries: typed ids for blocks/items/effects/entities/menus/block-entity types are stored with the content root and merged into `by_registry`/`summonable`, so `/summon`, `/give`, `/setblock` and `/fill` resolve mod namespaces.
- [x] Rank method-body call sites in the ABI census: per-jar and aggregate body-call/field-ref counts and bounded errors, with top-N helpers and summary output.
- [x] Inject NeoForge constructor arguments: supported `IEventBus`/`ModContainer`/`FMLModContainer`/`Dist`/`ModList`/`String` parameters are selected widest-first with no-arg fallback.
- [x] Report Mixin planning per jar: the game-facing compatibility report carries resolved plan/target counts, unresolved INVOKE selectors, readable configs and config errors, prints a deterministic `mixin:` summary line, and warns once when any of it does not run.
- [x] Keep unsupported native Mixin anchor modifiers explicit: FIELD/NEW/JUMP/Redirect plans with slices or non-`NONE` shift/by are report-only with a deterministic fallback reason; supported anchors remain executable.
- [x] Judge Mixin lifecycle phases in the JVM runner: after bootstrap and config registration it attempts `onLoadingDone`, resolves the default environment and sets the client/server side for the selected entry kind, reporting each step.
- [x] Record nested jar metadata: Fabric JiJ and NeoForge JarJar entries are discovered with bounded identity and errors folded into the per-jar info.
- [x] Summarise Java content declarations: a bounded `DeclarationSummary` merges typed tables and native data keys across mods with deterministic lines for logs/UI.
- [x] Provide bounded screen and datagen façades: Fabric `ScreenEvents`/`Screens`, NeoForge `ScreenEvent` markers, and Fabric `DataGeneratorEntrypoint`/`FabricDataGenerator`/output/provider retention. The JVM runner also accepts `--entry-kind datagen` and `--datagen-output`, invokes `onInitializeDataGenerator` and reports retained providers; generation itself is not implemented.
- [x] Provide bounded model-loading façades: Fabric `ModelLoadingRegistry`/`ModelProviderContext` and NeoForge `ModelEvent` registration retain providers, requested ids and model keys in deterministic order, emitted only when the real API is absent.
- [x] Inherit loot from the entity template: declared aliases fall back to their vanilla template table, explicit mod tables win, and non-alias behavior is unchanged.
- [x] Apply declared entity categories and spawn rules: aliases canonicalise a mob category, retain bounded spawn restrictions, feed placement/heightmap tables, and expose the template for loot. The height window itself is still decided in the vanilla spawn selector.
- [x] Make declared mod entities summonable: resource loading scans `data/*/horizon/entity/*.json`, `MobTypes` clones the declared vanilla template with bounded overrides, and `/summon <ns>:<id>` resolves through the alias table. Entities are now consumed by gameplay; menus and block entities are not.
- [x] Hand supplied jars to Fabric Loader through a bounded `-Dfabric.addMods` property (plus opt-in `--fabric-development`), with a read-back diagnostic. Opt-in `--fabric-discovery` runs the loader's own discovery and reports declared/found/missing ids.
- [x] Bind menus to blocks in the server snapshot: `menus_for_block`, bounded `menu_bindings`, diagnostics, and atomic rejection of undeclared block targets.
- [x] Bind menus to blocks: menu declarations carry bounded `open_blocks` ids cross-checked against declared/vanilla blocks and block-entity valid blocks, with a `menus_for_block` accessor.
- [x] Provide bounded menu/screen-handler façades: Fabric extended menu types/providers retain the wrapped type, codec and opening data with game-jar role resolution; NeoForge container factories and `IMenuTypeExtension` retain factories/natural ids on the generated `MenuType` stub.
- [x] Fold nested jar metadata into the census: per-jar and aggregate rows carry sorted Fabric JiJ/NeoForge JarJar identities, per-kind counts and bounded metadata errors, with a deterministic summary line.
- [x] Log the merged Java content declaration summary at startup and append bounded declared counts to the aggregate compatibility line.
- [x] Provide bounded attachment façades: Fabric `AttachmentRegistry`/`AttachmentType`/`AttachmentTarget` retain ids, codecs, initializers and flags with a bounded per-target store, and NeoForge `AttachmentType` builders retain the same registration shape.
- [x] Round-trip the native declaration set: `from_native` emits `data/<id>/horizon/{block,item,mob_effect,entity,data_component,attachment,menu,block_entity}/*.json`, and `Content::read` accepts and validates every kind with the same parsers and bounds, so a native content root survives export and re-read.
- [x] Discover and report Mixin configs in the JVM fallback: Fabric/NeoForge metadata and root `*.mixins.json` entries are read from the supplied jars, parsed tolerantly (`package`, `mixins`, `client`, `server`, `required`, `priority`), logged deterministically, and passed to the JVM as a bounded `-Dmixin.configs` property before `org.spongepowered.asm.launch.MixinBootstrap.init` is attempted. After bootstrap, each config is registered through `org.spongepowered.asm.mixin.Mixins.addConfiguration`, with missing/partial failures reported rather than fatal.
